# Crazy Elevator agent rules

The playable game lives in `Assets/Scenes/Main.unity`. Use that **one scene** for both solo and 1v1. `CottonCandyWorld.unity` is an art preview, not a second game flow. Keep the tech demo playable after each change.

## Ownership (Liam diagram)

Follow the manager diagram in `Assets/Scripts/README.md`.

| Owner | Owns |
| --- | --- |
| `GameManager` | Round / session, timer, score, view mode |
| `MenuManager` | Mode select, pause, overlays |
| `InputManager` | Raw controls → game actions |
| `SfxManager` / `MusicManager` | Audio |
| `ElevatorManager` + `PassengerManager` | One pair **per elevator** (player + NPC in 1v1) |
| `ElevatorMatch` | Second elevator / 1v1 coordination |

### Scene GameObjects — required

**Put each global manager on its own named GameObject in Main and attach its script in the Inspector.** Do not hide required globals behind runtime `new GameObject` or `AddComponent`.

Expected Hierarchy roots (names may vary slightly, but must be findable):

- `GameManager` → `GameManager`
- `InputManager` → `InputManager`
- `SfxManager` → `SfxManager`
- `MusicManager` → `MusicManager`
- `MenuManager` → `MenuManager`
- `Player Elevator` (or equivalent) → `ElevatorManager` + `PassengerManager` (+ `ElevatorMatch` is fine here)
- Prefab / art roots for cabin, shaft, world (not generated by gameplay scripts)

NPC elevator may be **instantiated for 1v1**, but its manager components must stay easy to find and inspect.

Singletons are mostly semantic so we can move logic later — they still need **visible scene objects**, not invisible bootstraps.

## Keep it simple

- Prefer **small methods**, clear public serialized refs, and code a beginner can follow.
- **No god classes.** Extend the existing responsible component before inventing a new system.
- **Do not multiply scripts.** Avoid a new `.cs` file for every tiny helper. One manager box = one (or a few partial) scripts.
- Prefer **serialized Inspector references** over `FindObjectOfType` / silent runtime wiring when a reference is required for the Main scene.
- One folder level below a feature folder when possible. Keep `.meta` / GUIDs intact when moving assets.

## Art vs gameplay

Gameplay and art must stay separable.

- Cabin, shaft, passengers, scenery = editable **GameObjects, prefabs, meshes, materials, or ProBuilder**.
- Scripts may **move / animate / enable** those objects.
- **Do not generate detailed 3D geometry in gameplay code.** If you are about to `new` meshes, cubes, or procedural props for look — stop and use a prefab / ProBuilder object instead.
- Existing editable geometry: `Assets/Static/ElevatorPersonas/Prefabs/` and related Static folders.

## Gameplay product rules

- World order: office (floors 0–3), candy (4–7), underwater (8–11). Keep the start friendly to new players.
- Do not change the three-minute delivery-score win condition without team agreement.
- HUD / help text: short and readable. Prefer a focused feedback cue over another permanent panel.
- Do not trade usable cabin space (or the outside view) for decoration or oversized UI (patience bars, overlays).
- Kick / board / travel feedback should stay fun and readable; do not silently drop existing animations without a replacement.

## Before finishing

- Check solo and 1v1, world order, boarding, kicking, travel, timer, and audio after relevant changes.
- Verify compilation. When editing layout or managers, confirm Main Hierarchy still has the named manager objects above.
- Preserve teammates' local edits. Do not commit or push unless the user asks.
